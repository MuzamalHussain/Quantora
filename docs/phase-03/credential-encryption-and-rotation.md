# Credential encryption and rotation

cryptography 50.0.1 AESGCM provides AES-256-GCM with random 96-bit nonces and full tags. Ciphertext has version=1, key_id, nonce and encrypted bytes. AAD canonically binds record ID, tenant, provider, environment and scope. A unique index checks key-ID/nonce uniqueness among stored credentials. Wrong/missing keys, modified ciphertext and tenant/environment swaps cannot decrypt. No custom cipher/password algorithm is implemented.

External bootstrap injects a base64 32-byte keyring in QUANTORA_CUSTODY_KEYS and selects QUANTORA_ACTIVE_KEY. Root keys are not stored in Mongo, source, browser, logs or backup archives. This local environment provider is an interface to future managed key custody; it is not the user-facing integration flow. User provider credentials are submitted through authenticated Settings > Integrations, encrypted server-side and returned only as fixed masked metadata. Audit/event output never includes submitted credentials. Synthetic values only are used in tests.

Create, replace, disable and remove are tenant-scoped, audited transactions. Create requires verified local email. Tenant owners use BINANCE TESTNET/LIVE; admins use platform NEWS/MACRO. All stored connections remain UNVERIFIED. No Test Connection success, exchange permissions claim or external request occurs. Replacement checks existing ciphertext recoverability before encrypting the new value. Disable/removal report only local storage changes, never exchange-side revocation.

The obligation interface defaults to UNKNOWN/deny. The application explicitly supplies no-execution capability only while the canonical foundation HEALTH contract fixes trading_enabled=false. Changing that contract must introduce a reconciled obligation checker; unknown/true capability rejects replacement/removal. This is a phase-specific structural guard, not a permanent flat-position assumption.

Rotation is an explicit operator command: retain old keys, add/select a new key ID in external custody, then `python -m quantora_api.manage rotate`. Each current record is decrypted/re-encrypted with fresh nonce and transactionally advances its revision, audit and progress. The rotations record stays RUNNING on interruption; rerun skips already-converted records and finishes COMPLETE. Concurrent writes use current transactional state, not a stale plaintext snapshot. Keep old keys until current records and every retained backup/mailbox no longer require them. Rotation tests interrupt after one record and resume; never rotate working user data as part of verification.
