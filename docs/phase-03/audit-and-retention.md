# Audit and retention

Application audit interfaces append only. Records include event ID, actor/tenant when known, fixed action/target references, UTC timestamp, correlation ID and a sanitized SUCCESS/DENIED/FAILED outcome. Passwords, provider secrets, reusable session/recovery tokens, request bodies and arbitrary exception text are excluded. Actual mutation and audit records share Mongo transactions: failure of the required audit write rolls back critical mutations. Login failure and unauthorized admin access generate explicit denied events. Migration and credential rotation are audited; backup/restore record metadata without paths or key bytes.

The runtime role specification permits audit insert/find, not update/remove; migrations and operator utilities are separate roles conceptually. The supplied local Mongo server has authentication disabled, so a local database administrator can still change data. These records are not cryptographically immutable or tamper-proof. Before nonlocal use, enforce authenticated least-privilege Mongo principals and complete production security review. Redis stores only expiring abuse counters, never authoritative users, sessions, audit or financial state. Rate-limit failure returns 503.

D-12 remains unapproved. No jurisdiction, legal retention period, hold authority, shared-training permission or trained-artifact deletion policy is invented. Development defaults: sessions eight hours and recovery tokens 15 minutes, with TTL solely as cleanup; all actual authorization checks enforce expiry independently. No TTL is applied to audit, idempotency or financial foundations. Profiles/accounts have no deletion API in this phase; public metadata export is self-scoped and excludes secrets. Expired encrypted development mailbox files may be removed by their local owner under a documented local policy; they are never treated as financial/audit history. Production tenant collection/deletion/retention promises remain blocked pending D-12.
