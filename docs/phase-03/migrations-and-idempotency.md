# Migrations and idempotency

`python -m quantora_api.manage migrate` explicitly applies v1; the web process never silently migrates. A unique durable migration_lock record excludes concurrent runners. The lock has no timed takeover: a process crash cannot let a second runner overlap a still-running first. Normal exceptions release only the matching lock owner. After a crash, inspect the recorded owner and establish the old process stopped, then use `unlock-migration --lock-owner EXACT_OWNER` before retrying. Never clear an unknown active lock or reset collections.

The runner creates strict validated collections and required indexes non-destructively. Existing validators must match, and Mongo index option conflicts fail. Before each uniqueness index it aggregates duplicate keys and stops if conflicts exist; it deletes nothing. Migration completion and its audit event commit together. A failed partial run has no completed history record and can safely resume compatible already-created collections. A changed completed checksum requires a new migration, not rewriting v1. Tests cover first/repeat execution, interruption, held lock, validator mismatch, uniqueness enforcement and duplicate preflight.

Settings updates demonstrate a reusable transaction-bound idempotency primitive. Keys are scoped by authenticated tenant and operation; fingerprint is SHA-256 of canonical JSON. Same key/same payload returns the stored result; differing payload is rejected. Mutation, sanitized audit and result record commit atomically. Concurrent duplicate-key losers read the committed winner, never repeat effects outside the transaction. PyMongo with_transaction handles retryable transaction/unknown-commit outcomes; callbacks contain only database operations and no external delivery. If the client loses a response, retry the same key and body, not a new key. No TTL expires the deduplication record in this phase.

Mongo transactions do not make a future exchange order atomic. No remote order dispatch exists. Future durable intents, fencing, reservation and reconciliation remain the Phase 2 design boundary and later execution work.
