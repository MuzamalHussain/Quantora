# Phase 3 — SaaS and data foundation

Current Windows development startup, account creation, local mail and interactive admin bootstrap are documented in `../local-startup-repair-checkpoint.md`; the manual commands below remain the original Phase 3 procedure.

Current status is in phase-03-report.md and evidence/gate-latest.json. Read continuation-checkpoint.md before resuming. This phase extends the existing FastAPI API and React workspace; Rust health/ping and disabled trading are preserved. It provides local accounts, sessions, tenant-owned settings, encrypted integration storage, migration/transaction/audit primitives and isolated restore tooling. No exchange calls or Phase 4 ingestion exist.

From the project root, use the existing virtual environment and locks. Set server process configuration explicitly; .env is not loaded automatically. Start Mongo/Redis using the existing Phase 2 Compose instructions without deleting volumes. From services/control-api run `../../.venv/Scripts/python.exe -m quantora_api.manage migrate` once; repeats check compatibility. Then run `../../.venv/Scripts/python.exe -m quantora_api`. Start frontend using the existing `npm run dev` and open Account. The chart remains a public fixture demonstration; account APIs require server-resolved authentication.

Provider custody/local recovery delivery require `QUANTORA_CUSTODY_KEYS` (JSON mapping key ID to base64 32-byte externally supplied key), `QUANTORA_ACTIVE_KEY`, and `QUANTORA_LOCAL_MAIL_DIR` (a private local directory such as the project .cache/local-mail). Do not paste keys into shell history, source files, chat or committed configuration. Supply these through trusted process secret injection; preserve existing keys. Missing custody keys prevent secret operations. Missing delivery configuration prevents recovery delivery. Production profile is rejected: external delivery, TLS deployment, authenticated database provisioning and D-12 production policy are not configured here.

Run `.venv/Scripts/python.exe scripts/verify_phase03.py` from root. It invokes the previous-phase gate and real isolated Phase 3 browser checks. Database integration tests use UUID-named test databases, synthetic secrets and independent transient rate-limit prefixes. No working application database is dropped. PASS requires every mandatory gate; blocked dependencies are not replaced by mocks.
